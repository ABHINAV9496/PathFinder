# Design: Make JobbLoot work for any profession, any user, zero-config

Date: 2026-07-31
Status: Approved (sections presented to user; user: "ok you can start")

## Goal

Anyone who clones JobbLoot can use it for any profession (not just Python
developer) with zero manual configuration:

- The profile (single user per install) drives everything: skill matching,
  search queries, fetcher sources, salary expectations, cover letters.
- The FastAPI CV Engine is the single engine for tailored resumes **and**
  cover letters, built from the user's **uploaded original resume + profile**.
- A fresh clone runs with no manual config steps.
- Live data (`db.sqlite3`) is never deleted.

## Decisions (from user)

1. CV generation = FastAPI service; it must use **both** the uploaded original
   resume and the profile for the tailored resume.
2. Job fetching = profile-driven queries, pluggable sources.
3. Single-user per install.
4. Fresh clone = zero-manual-config run.
5. Cover letters also generated by the CV Engine from resume + profile.
6. During implementation, if additional agent skills are needed, use
   `find-skills` (`npx skills find`) to discover them; install only with
   explicit user approval.

## 1. Zero-config bootstrap

- `setup.py`:
  - Copy `.env.example` → `.env` (idempotent), generate `DJANGO_SECRET_KEY`
    if missing.
  - Auto-create a default `profile.json` if absent (does not overwrite
    existing).
  - Do **not** touch an existing `db.sqlite3`.
- Fix `apps/jobs/matcher.py` fresh-clone crash: module-level
  `from config.profile import SKILL_WEIGHTS` and `_profile = load_profile()`
  must degrade gracefully when `config/profile.py` / `profile.json` are
  missing (default to profile-driven matching with empty skill set rather
  than ImportError).

## 2. Generic, profile-driven profile model

- Skill weights / aliases / categories computed from the profile's own
  skills instead of hardcoded `python/django/drf/...` lists in both Django
  and cv-engine.
- `config/constants.py`: `REJECT_ROLE_KEYWORDS` (rejects non-Python roles)
  and `NORTH_INDIA_STATES` become inactive/no-ops (or profile-driven); a
  cloner of any profession must not be filtered out by default.
- Salary extraction in `apps/jobs/services/core.py`: generalize `SALARY_PATTERNS`
  from ₹/LPA-only to currency-aware (`$`, `€`, `£`, `K/yr`, `LPA`, etc.).
- `MIN_SALARY` and other thresholds read from profile (`looking_for` /
  `min_salary`) with safe defaults.

## 3. Pluggable, profile-driven fetching

- `config/queries.py`: `SEARCH_QUERIES` / `TECHNOPARK_QUERIES` /
  `CUTSHORT_SEARCH_URLS` / `JOBDROP_QUERIES` derived from profile
  `role` / `looking_for` / `location` instead of hardcoded python/Kerala.
- Fetcher registry: each source enabled per profile; any source that
  fails degrades gracefully (logged, contributes 0) and never crashes or
  stalls the pipeline.

## 4. Fix jobdrop fetching (root-caused from live run logs)

Observed: `google`/`ashby`/`greenhouse`/`workday` hit Google `/sorry/`
CAPTCHA; `zip_recruiter` returns HTTP 403; the playwright/zendriver-based
`google` scraper throws `NotImplementedError` from
`asyncio.create_subprocess_exec` (no browser subprocess support from
Django's background thread on Windows); result: `jobdrop: contributed 0 jobs`
every run.

Fixes:
- Prune `JOBDROP_SOURCES` to browser-free/API sources that work:
  `remoteok`, `weworkremotely`, `the_muse`, `adzuna`, `jooble`, `findwork`,
  `naukri`, `wellfound`. Drop `google`, `zip_recruiter`, `ashby`,
  `greenhouse`, `lever`, `workday`. List becomes profile-configurable.
- Fix `site` → `site.value` so `source` is `jobdrop:remoteok` (not
  `jobdrop:Site.REMOTEOK`).
- Surface `df.attrs["per_source"]` telemetry (per-site count/error/timing)
  into logs and fetch stats.
- Add `hours_old=72`, cap `results_wanted` (~30).
- Replace hardcoded `country_indeed="india"` with profile country;
  treat "Remote" location as `is_remote=True`.
- Keep `_safe_fetch` graceful degradation.

## 5. Fix cutshort `NoneType` bug

`apps/jobs/fetchers/cutshort.py` nested `.get()` chain can hit a `None`
`dehydratedState` → `'NoneType' object has no attribute 'get'` on some
pages. Guard each level with `or {}`.

## 6. CV Engine = single resume + cover-letter engine

- Django delegates all CV generation to the FastAPI service; request carries
  the pypdf-extracted **original resume text** (from `CredStore.resume_file`)
  **plus** the profile.
- CV Engine: profession-agnostic section order / categories / tailoring
  driven by profile skills/categories rather than fixed
  header/summary/skills/experience/projects/education.
- New `/v1/generate-cover-letter` endpoint: template-based by default,
  LLM-upgraded when AI settings are present; absorbs
  `apps/jobs/views/cover_letter.py`, `apps/jobs/views/generate_template_cl.py`
  and `apps/jobs/cv_engine/cover_templates.py`.
- Keep `X-Service-Key` auth and graceful degradation when the engine is down.

## 7. Frontend

- Profile page already exposes the fields + resume upload; adjust only what
  the API changes touch.

## 8. Data-safety constraints (critical)

- Never delete/truncate/reset `db.sqlite3` (contains application history:
  Application, Job, RawJob, JobEvent, DailyStats, CredStore, AIConfig).
- Backup `db.sqlite3` before any schema work (`backups/`, gitignored).
- Tests run against in-memory SQLite (`config.settings.test`), never the
  live DB; fresh-clone test uses a scratch DB path.
- Migrations are additive only; review every generated migration.

## 9. Tests + bug-fix pass (tests-first)

- Fresh-clone test (no profile/config → app boots, fetcher runs, CV
  generation degrades gracefully).
- Multi-profession tests (data analyst, designer, marketing), non-India
  location, missing-config permutations, currency variety.
- Cover-letter-from-resume+profile tests; CV Engine tests.
- Jobdrop pruning regression; cutshort `NoneType` regression.
- Use systematic-debugging for any bug found.
